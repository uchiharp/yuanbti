# 架构对抗评审 Prompt

评分通过后，对架构方案进行一次性对抗评审。一个 prompt 同时扮演四个视角，输出分歧点和风险项。

## 评审视角

### 1. 开发1 视角（技术可行性）
- 技术选型是否合理，是否有更好的替代方案
- 接口设计是否可实现，是否有过度设计
- 技术栈版本是否稳定，是否有已知坑
- 代码架构是否可实现，是否有逻辑 bug

### 2. 开发2 视角（技术实现）
- 代码结构和模块划分是否清晰
- 技术债是否可控，偿还计划是否合理
- 数据模型是否满足业务需求
- 边界条件和异常处理是否完整

### 3. QA 视角（可测试性）
- 测试覆盖策略是否合理
- 日志和监控是否足够定位问题
- 自动化测试方案是否可行
- docker-compose.test.yml 是否合理
- 验收标准是否可测试

### 4. PM 视角（需求完整性）
- PRD 中的所有 REQ 是否在架构中有对应设计
- 优先级排序是否合理
- 架构设计是否覆盖了所有业务场景
- 逻辑闭环是否有漏洞或冲突
- Out of Scope 是否会影响核心功能

## 输出格式

```markdown
## 架构交叉评审报告

### 🔴 阻断项（必须修复才能进入下一阶段）
- [视角] 问题描述 → 建议修复方式

### 🟡 风险项（建议修复，可带风险进入下一阶段）
- [视角] 问题描述 → 建议修复方式

### 🟢 观察项（供下游参考）
- [视角] 观察内容

### 一致性检查
- 各视角是否有分歧：是/否（如 开发1 认为选型A好但 开发2 认为选型B好）
- 分歧详情：（如有）

### 评审结论
- 阻断项数量：X
- 风险项数量：X
- 观察项数量：X
- 结论：评审通过 / 评审未通过

### 质量评分参考
- 架构质量评分：{score}/{max_score}（{grade}）
- 6维度覆盖：{X}/6
- 工程健壮性覆盖：{X}/11
```

## 评审规则
- 评审只发现问题，不修改 ARCHITECTURE.md
- 阻断项 = 0 个时，评审自动通过
- 阻断项 > 0 时，需要用户决定：修复后重评 / 带风险继续
- 评审结果写入 cross-review-arch.md
- 每个视角至少提出 2 个观察项

## 阻断项判定标准

以下情况必须列为阻断项：
- 技术选型无对比，只有单选
- 数据模型只有表名没有字段
- 关键业务流程在架构中无对应设计
- 安全措施完全缺失
- 风险识别为0
- 6维度分析覆盖不足3个
- 工程健壮性覆盖不足5项

## 风险项判定标准

以下情况列为风险项：
- 技术选型有对比但缺少 trade-off 分析
- 性能指标未量化
- 缓存策略未设计
- 部分 API 缺少错误码定义
- 连接池使用默认配置
