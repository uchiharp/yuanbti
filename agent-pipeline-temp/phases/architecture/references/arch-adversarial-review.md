# 架构对抗评审 Prompt

评分通过后，对 ARCHITECTURE.md 进行四角色对抗评审。每个角色独立输出评审意见。

## 评审视角

### 1. RD 视角（技术可行性）
- 技术选型是否合理？是否有更好的替代方案？
- 接口设计是否可实现？是否有过度设计？
- 数据模型是否支持业务需求？字段类型是否合理？
- 代码架构分层是否清晰？模块耦合度如何？

### 2. 架构师视角（架构一致性）
- 整体架构是否自洽？各模块间是否一致？
- 设计模式是否恰当？是否有反模式？
- 扩展性设计是否足够？未来需求变化能否低成本适配？
- 6维度技术特性分析是否充分？

### 3. QA 视角（可测试性）
- 架构是否支持测试隔离？mock 策略是否可行？
- 日志设计是否足够排查问题？是否有 traceId？
- 覆盖率工具是否配置？测试环境是否定义？
- 11项工程健壮性是否可验证？

### 4. PM 视角（需求完整性）
- PRD 中的每个 REQ 是否都有对应的架构决策？
- 优先级是否合理？P0 功能是否有足够保障？
- 逻辑是否闭环？是否有遗漏的用户场景？
- 非功能需求（性能、安全）是否有量化指标？

## 规则
- 评审只发现问题，不修改 ARCHITECTURE.md
- 阻断项 = 0 个时，评审自动通过
- 阻断项 > 0 时，需要架构师修复后重审
- 评审结果写入 cross-review-arch.md
- 总轮次 ≤2
