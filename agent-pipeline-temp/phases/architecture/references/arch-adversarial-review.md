# 架构对抗评审 Prompt

评分通过后，对 ARCHITECTURE.md 进行一次性对抗评审。一个 prompt 同时扮演四个视角，输出分歧点和风险项。

## 评审视角

### 1. 开发1视角（技术可行性）
- 技术选型是否在团队能力范围内，是否有学习曲线风险
- 接口设计是否合理，是否存在过度设计或设计不足
- 数据模型是否可实现，是否有性能瓶颈
- 依赖的第三方库/服务是否稳定可靠
- 架构方案中的假设是否成立

### 2. 开发2视角（技术实现）
- 代码结构是否清晰，模块划分是否合理
- 分层是否严格，是否存在跨层调用
- 技术债识别是否充分，是否有隐性债务
- 扩展点设计是否实用
- 日志/异常处理是否可落地

### 3. QA视角（可测试性）
- 测试策略是否完整（单元/集成/E2E）
- docker-compose.test.yml 是否能一键启动
- 覆盖率配置是否可执行
- 日志是否足以定位问题
- 边界条件和异常场景是否有测试路径
- 性能指标是否有可测试的量化目标

### 4. PM视角（需求完整性）
- 架构方案是否完整覆盖 PRD 中的所有 REQ
- 优先级是否与 PRD 一致
- 非功能需求（性能/安全/扩展）是否满足
- 是否有遗漏的关键场景
- 架构决策是否影响产品交付时间

## 输出格式

```markdown
## 架构对抗评审报告

### 🔴 阻断项（必须修复才能继续）
- [视角] 问题描述 → 建议修复方式

### 🟡 风险项（建议修复，可带风险继续）
- [视角] 问题描述 → 建议修复方式

### 🟢 观察项（供下游参考）
- [视角] 观察内容

### 一致性检查
- 各视角是否有分歧：是/否（如 PM 认为P0但开发认为不急）
- 分歧详情：（如有）

### 结论
- [ ] 评审通过
- [ ] 评审未通过（阻断项 > 0）
```

## 规则
- 评审只发现问题，不修改 ARCHITECTURE.md
- 阻断项 = 0 个时，评审自动通过
- 阻断项 > 0 时，需要用户决定：修复后重评 / 带风险继续
- 评审结果写入 cross-review-arch.md
