# 技术 Spike 方法论

> Spike 是敏捷开发中的"探针"——用最小成本验证关键技术可行性。

---

## 1. 什么是 Spike

Spike 是一个**时间盒限制**的技术调研或原型验证任务，目的是：
- 降低技术风险
- 验证技术方案可行性
- 获得足够信息做出架构决策

**Spike ≠ 实现**：只验证关键技术点，不做完整功能。

---

## 2. 何时触发 Spike

| 触发条件 | 示例 |
|---------|------|
| 架构文档标注"高风险" | 新技术栈引入、复杂集成 |
| 架构文档标注"需验证" | 性能目标不确定、安全方案待确认 |
| 评审发现技术可行性疑问 | "这个方案真的能支撑 1000 QPS 吗？" |
| 技术选型有 ≥2 个方案无法决策 | "Redis vs Memcached 选哪个？" |

---

## 3. Spike 执行规范

### 时间盒
- **单个 Spike ≤ 2h**
- **总 Spike 时间 ≤ 4h**
- 超时视为"不通过"，需要换方案

### 验证方法矩阵

| 验证类型 | 方法 | 产出 |
|---------|------|------|
| 技术可行性 | 最小原型 + 核心 API 调用 | 代码 + 结论 |
| 性能验证 | 基准测试（wrk/JMeter/k6） | 测试数据 + 结论 |
| 集成验证 | 与外部系统联调原型 | 联调日志 + 结论 |
| 安全验证 | PoC 攻击测试 | 测试结果 + 结论 |
| 兼容性验证 | 多版本/多浏览器测试 | 兼容矩阵 + 结论 |

### 代码规范
- Spike 代码放在 `spike-*/` 目录
- **不合并到主分支**
- 可以有硬编码、magic number（目的是验证，不是交付）
- 验证完成后可删除

## 4. Spike 报告模板

```markdown
# Spike Report: {技术点}

## 背景
- 为什么需要验证：{风险描述}
- 时间盒：{N}h

## 验证方案
- 方法：{怎么做}
- 工具：{用什么}
- 指标：{怎么算通过}

## 执行过程
{步骤记录}

## 关键代码
```{language}
{核心代码片段}
```

## 测试数据
| 指标 | 目标 | 实际 | 结论 |
|------|------|------|------|
| QPS | ≥1000 | 1200 | ✅ |
| 延迟 P99 | <100ms | 85ms | ✅ |

## 结论
- ✅ 通过：{原因}
- ❌ 不通过：{原因}
- ⚠️ 有条件通过：{条件}

## 发现
- 新约束：{如有}
- 新风险：{如有}
- 建议：{如有}
```

---

## 5. 结论路由

| 结论 | 路由 |
|------|------|
| 全部通过 | 推进下一阶段 |
| 部分不通过 | 回退架构设计，针对性调整 |
| 全部不通过 | 回退架构设计，重新选型 |
| 有条件通过 | 记录条件，推进但标记风险 |

---

## 6. 反模式

| 反模式 | 正确做法 |
|--------|---------|
| Spike 变成了完整实现 | 只验证关键技术点 |
| 不设时间盒，无限调研 | 严格 ≤2h/个，≤4h 总计 |
| Spike 代码合入主分支 | 保持独立，验证完可删 |
| 只做文档调研不写代码 | 必须有可运行的代码原型 |
| 结论模糊（"可能可行"） | 必须明确：通过/不通过/有条件 |
