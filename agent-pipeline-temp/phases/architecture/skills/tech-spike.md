# 技术 Spike 方法论

> 本 skill 供 Spike Agent 在阶段 2.8 执行技术验证时参考。

---

## 什么是 Spike

Spike 是一种**时间盒限制的技术调研/原型验证**，目的是在投入大量开发资源前，确认关键技术方案可行。

### Spike 的特点

- **时间限制**：通常 2-4 小时，超时视为不通过
- **目标明确**：只验证一个具体技术点
- **可丢弃**：验证代码不合并到主分支
- **结论导向**：必须给出通过/不通过/有条件通过的明确结论

---

## Spike 类型

| 类型 | 目的 | 示例 |
|------|------|------|
| 技术可行性 | 验证某技术/库/API 能否实现需求 | 第三方支付 API 集成 |
| 性能验证 | 验证方案能否满足性能指标 | 1000 QPS 下的响应时间 |
| 集成验证 | 验证多个组件能否协同工作 | 前后端 + 数据库联调 |
| 安全验证 | 验证安全方案是否有效 | JWT + RBAC 完整流程 |
| 数据验证 | 验证数据模型能否支撑业务 | 复杂查询的执行计划 |

---

## Spike 执行流程

### 1. 准备阶段（15分钟）
- 明确验证目标：要证明什么？
- 定义成功标准：怎样算通过？
- 确定验证方法：怎么验证？
- 准备环境：需要什么工具/服务？

### 2. 执行阶段（2-3小时）
- 搭建最小可运行原型
- 执行验证测试
- 记录关键数据（性能数据、API 响应、错误日志）
- 发现额外风险或约束

### 3. 总结阶段（30分钟）
- 整理验证结论
- 记录代码片段和关键日志
- 评估新发现的风险
- 给出明确结论

## Spike 报告格式

```markdown
# SPIKE-REPORT.md

## 验证概要
- 项目：{PROJECT}
- 日期：{DATE}
- 时间投入：Xh
- 验证点数量：X

## 风险点 1: {描述}
### 验证目标
{要验证什么}

### 成功标准
{怎样算通过}

### 验证方法
{怎么验证}

### 代码片段
{关键代码}

### 验证结果
- 结论：✅ 通过 / ❌ 不通过 / ⚠️ 有条件通过
- 详情：{具体发现}
- 性能数据：{如有}

### 新发现的风险
{如有}

## 总结
- 通过：X 个
- 不通过：X 个
- 有条件通过：X 个
- 新发现风险：X 个
```

---

## 结论路由

| 情况 | 路由 | 说明 |
|------|------|------|
| 全部通过 | 推进下一阶段 | 架构方案可行 |
| 部分不通过 | 回退架构设计 | 针对性调整不通过的部分 |
| 全部不通过 | 回退架构设计 | 需要重新设计技术方案 |
| 有条件通过 | 记录条件，推进 | 在满足条件的前提下继续 |

---

## 常见陷阱

| 陷阱 | 正确做法 |
|------|---------|
| Spike 范围太大 | 拆分成多个小 Spike |
| 没有明确的成功标准 | 先定义成功标准再开始 |
| Spike 代码混入主分支 | 验证完就丢弃，只保留报告 |
| 超时还在继续 | 时间盒到了就停，视为不通过 |
| 只验证正常流程 | 也要验证异常/边界场景 |
