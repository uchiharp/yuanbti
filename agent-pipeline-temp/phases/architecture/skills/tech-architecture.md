# 技术架构设计方法论

> 架构师在设计阶段的核心参考。涵盖从技术选型到代码架构的完整设计方法。

---

## 1. 技术选型方法论

### 选型流程
1. **需求分析**：从 PRD 提取技术需求（性能、安全、扩展、团队）
2. **候选方案**：列出 ≥2 个可行方案
3. **对比矩阵**：按维度打分（1-5分）
4. **Trade-off 分析**：明确每个方案的代价
5. **决策记录**：选择理由 + 放弃理由

### 对比维度
| 维度 | 权重 | 说明 |
|------|------|------|
| 功能匹配度 | 高 | 能否满足 PRD 中的需求 |
| 性能 | 高 | QPS、延迟、资源消耗 |
| 社区活跃度 | 中 | GitHub stars、issue 响应、版本频率 |
| 学习成本 | 中 | 团队熟悉度、文档质量 |
| 运维复杂度 | 中 | 部署、监控、故障排查 |
| 扩展性 | 中 | 插件机制、定制能力 |
| 许可证 | 低 | 开源许可是否兼容 |

### 选型输出格式
```markdown
### {模块名} 技术选型

| 方案 | 功能 | 性能 | 社区 | 学习 | 运维 | 扩展 | 总分 |
|------|------|------|------|------|------|------|------|
| 方案A | 5 | 4 | 5 | 3 | 4 | 4 | 25 |
| 方案B | 4 | 5 | 3 | 4 | 3 | 3 | 22 |

**选择**: 方案A
**理由**: {为什么选A}
**代价**: {选A放弃了什么}
**缓解**: {如何缓解A的不足}
```

## 2. 分层架构设计

### 推荐分层
```
┌─────────────────────────────────┐
│         Presentation Layer      │  ← Controller / API Gateway
├─────────────────────────────────┤
│         Application Layer       │  ← Use Case / Service Facade
├─────────────────────────────────┤
│         Domain Layer            │  ← Entity / Value Object / Domain Service
├─────────────────────────────────┤
│         Infrastructure Layer    │  ← Repository / External API / MQ
└─────────────────────────────────┘
```

### 依赖规则
- **上层依赖下层**，下层不知道上层存在
- **Domain 层零依赖**：不依赖任何框架或基础设施
- **依赖倒置**：通过接口（Port）隔离基础设施（Adapter）
- **Controller 不直接调用 Repository**：必须经过 Service/Use Case

### 模块划分原则
- **按业务域划分**（DDD Bounded Context），不按技术层划分
- **高内聚低耦合**：模块内紧密协作，模块间通过接口通信
- **每个模块独立可测试**：mock 外部依赖即可单元测试

## 3. 数据模型设计

### 设计步骤
1. **实体识别**：从 PRD 的 REQ 中提取核心名词
2. **关系定义**：1:N、M:N、自关联
3. **字段定义**：类型、长度、约束、默认值
4. **索引策略**：主键、唯一索引、组合索引、全文索引
5. **软删除**：`deleted_at` 字段，不物理删除

### 字段规范
```markdown
| 字段名 | 类型 | 约束 | 说明 |
|--------|------|------|------|
| id | BIGINT | PK, AUTO_INCREMENT | 主键 |
| uuid | VARCHAR(36) | UNIQUE, NOT NULL | 对外暴露ID |
| name | VARCHAR(100) | NOT NULL | 名称 |
| status | TINYINT | NOT NULL, DEFAULT 0 | 状态枚举 |
| created_at | DATETIME | NOT NULL, DEFAULT NOW() | 创建时间 |
| updated_at | DATETIME | NOT NULL, DEFAULT NOW() | 更新时间 |
| deleted_at | DATETIME | NULL | 软删除标记 |
```

### 索引策略
- **查询频率高的字段**建索引
- **组合索引遵循最左前缀**
- **单表索引 ≤ 5个**（写入性能影响）
- **大表考虑分库分表阈值**（单表 > 1000万行）

## 4. API 设计规范

### RESTful 规范
```
GET    /api/v1/{resources}          → 列表查询
GET    /api/v1/{resources}/{id}     → 单条查询
POST   /api/v1/{resources}          → 创建
PUT    /api/v1/{resources}/{id}     → 全量更新
PATCH  /api/v1/{resources}/{id}     → 部分更新
DELETE /api/v1/{resources}/{id}     → 删除
```

### 统一响应格式
```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "meta": {
    "page": 1,
    "size": 20,
    "total": 100
  }
}
```

### 错误码体系
```
{MODULE}_{NUMBER}
AUTH_001  → Token 过期
AUTH_002  → 密码错误
PERM_001  → 无权限
SYS_001   → 参数校验失败
SYS_100   → 系统内部错误
```

### API 文档要素
- 请求方法 + 路径
- 请求参数（Query/Path/Body）+ 类型 + 必填/可选
- 响应格式 + 示例
- 错误码列表
- 认证方式
- 限流策略

## 5. 安全设计

### 认证方案选型
| 方案 | 适用场景 | 优势 | 劣势 |
|------|---------|------|------|
| JWT | 无状态 API | 无需服务端存储 | 无法主动失效 |
| Session | 传统 Web | 可主动失效 | 需要存储 |
| OAuth2 | 第三方登录 | 标准化 | 复杂度高 |

### 授权模型
- **RBAC**：基于角色的访问控制（适合大多数场景）
- **ABAC**：基于属性的访问控制（复杂权限场景）
- **权限粒度**：资源 + 操作（如 `user:read`, `user:write`）

### 数据安全清单
- [ ] HTTPS 强制
- [ ] 密码 bcrypt 存储
- [ ] 敏感字段 AES 加密
- [ ] API 限流防暴力破解
- [ ] CORS 白名单配置
- [ ] SQL 注入防护（参数化查询）
- [ ] XSS 防护（输出转义）
- [ ] CSRF Token

## 6. 架构决策记录（ADR）

每个重要架构决策都应该记录：

```markdown
## ADR-{N}: {决策标题}

### 状态
已接受 / 已废弃 / 已替代

### 上下文
{为什么需要做这个决策}

### 决策
{做出了什么决策}

### 后果
- 正面：{好处}
- 负面：{代价}
- 风险：{可能的问题}
```
