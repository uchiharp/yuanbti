# 架构审查方法论

> 多角色交叉评审架构方案的标准化流程和评分体系。

---

## 1. 评审维度（12维度）

| # | 维度 | 权重 | 评审要点 |
|---|------|------|---------|
| 1 | 技术选型 | 高 | ≥2个备选、trade-off 分析、团队匹配度 |
| 2 | 分层架构 | 高 | 依赖方向正确、层次职责清晰、无跨层调用 |
| 3 | 数据模型 | 高 | 字段定义完整、索引策略、软删除、时间字段 |
| 4 | API 设计 | 高 | RESTful 规范、错误码体系、版本管理 |
| 5 | 安全设计 | 高 | 认证授权、数据加密、API 安全、审计日志 |
| 6 | 性能设计 | 中 | QPS/延迟目标、缓存策略、数据库优化 |
| 7 | 扩展性 | 中 | 水平扩展、功能扩展、数据扩展 |
| 8 | 可测试性 | 中 | 测试隔离、mock 策略、覆盖率工具 |
| 9 | 可观测性 | 中 | 日志、监控、链路追踪、告警 |
| 10 | 健壮性 | 高 | 11项工程健壮性覆盖度 |
| 11 | 需求覆盖 | 高 | PRD REQ 全覆盖、无遗漏 |
| 12 | 文档质量 | 低 | 行数、结构、图表、可读性 |

---

## 2. 评分规则

### 单维度评分
- **5分**：优秀，超出预期
- **4分**：良好，满足要求
- **3分**：合格，有改进空间
- **2分**：不足，需要补充
- **1分**：严重不足，必须修改
- **0分**：缺失

### 总分计算
总分 = Σ(维度分 × 权重) / Σ(权重) × 20（归一化到100分制）

### 评级
| 评级 | 分数 | 含义 |
|------|------|------|
| EXCELLENT | ≥ 90 | 可直接进入开发 |
| GOOD | 75-89 | 小修后可用 |
| ACCEPTABLE | 60-74 | 需要补充关键内容 |
| NEEDS_WORK | < 60 | 必须大幅修改 |

---

## 3. 角色评审视角

### RD（开发视角）
- 技术方案是否可实现？
- 接口设计是否合理？
- 是否有过度设计？
- 代码结构是否清晰？

### 架构师（架构视角）
- 分层是否合规？
- 模块耦合度如何？
- 设计模式是否恰当？
- 扩展性是否足够？

### QA（测试视角）
- 是否支持测试隔离？
- 日志是否足够排查问题？
- 是否有故障注入点？
- 覆盖率工具是否配置？

### PM（需求视角）
- PRD 中的 REQ 是否全覆盖？
- 优先级是否合理？
- 逻辑是否闭环？
- 是否有遗漏场景？

## 4. 评审输出格式

```markdown
## 架构评审报告

### 评分总览
| 维度 | 得分 | 说明 |
|------|------|------|
| 技术选型 | 4/5 | ... |
| ... | ... | ... |
| **总分** | **XX/100** | **GOOD** |

### 🔴 阻断项（必须修复）
- [角色] 问题描述 → 建议修复

### 🟡 风险项（建议修复）
- [角色] 问题描述 → 建议修复

### 🟢 观察项（供参考）
- [角色] 观察内容

### 一致性检查
- 各视角是否有分歧：是/否
- 分歧详情：（如有）

### 结论
- 阻断项: X 个
- 风险项: X 个
- 评审通过 / 评审未通过
```

## 5. AI味检测

架构文档中常见 AI 生成痕迹：

| AI味特征 | 检测方法 | 扣分 |
|---------|---------|------|
| 过度使用"确保"、"实现" | 词频统计 | -1 |
| 章节内容空洞、无具体数字 | 关键指标缺失检查 | -2 |
| 万金油方案（"使用 Redis 缓存"） | 是否有具体 key/TTL 设计 | -1 |
| 缺少 trade-off 分析 | "选择X"但不说"放弃Y" | -2 |
| 风险识别模板化 | 是否结合项目具体情况 | -1 |

---

## 6. 评审规则

1. **评审只发现问题**，不修改架构文档（修改由架构师做）
2. **阻断项 = 0** 时，评审自动通过
3. **阻断项 > 0** 时，架构师必须修复后重审
4. **总轮次 ≤ 2**（初审 + 复审算 1 轮）
5. **评审必须基于文档内容**，不靠想象
6. **每个发现必须分类**：[actionable] / [trade-off] / [noise]
