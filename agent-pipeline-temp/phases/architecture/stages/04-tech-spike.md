# 阶段4: 技术 Spike（tech-spike）

## 任务
针对架构设计中识别出的高风险技术点，进行快速原型验证，确认技术方案可行后再进入入库阶段。

## 前置条件
- ARCHITECTURE.md 中存在高风险标记（`高风险`/`Spike`/`需验证`）
- 或用户/评审明确要求验证某个技术点

## 角色
- **Spike Agent**：执行技术验证（可以是架构师或指定开发）
- **协调者**：调度、收集结论、决定是否回退

## 执行流程

1. 读取 ARCHITECTURE.md 中标记为「高风险」或「需验证」的技术点
2. 对每个风险点执行 Spike 验证：
   - 搭建最小可运行原型
   - 验证关键技术 API/库/框架的可行性
   - 记录验证结论（通过/不通过/有条件通过）
3. 产出 SPIKE-REPORT.md
4. 结论路由：
   - **全部通过** → 推进 finalize
   - **部分不通过** → 回退 arch-design，针对性调整架构
   - **全部不通过** → 回退 arch-design，重新设计

## Spike 验证方法

### 验证类型
| 类型 | 方法 | 产出 |
|------|------|------|
| 技术可行性 | 搭建最小原型，验证核心 API | 代码片段 + 结论 |
| 性能验证 | 基准测试，验证 SLA 目标 | 测试数据 + 结论 |
| 集成验证 | 与外部系统联调原型 | 联调日志 + 结论 |
| 安全验证 | PoC 攻击测试 | 测试结果 + 结论 |

### 时间盒
- **单个 Spike ≤ 2h**
- **总 Spike 时间 ≤ 4h**
- 超时视为不通过

## SPIKE-REPORT.md 格式

```markdown

## 概要
- 项目: {项目名}
- 日期: {日期}
- 时间盒: 4h
- 实际耗时: {实际}

## 验证技术点

### Spike-1: {技术点名称}
**风险描述**: {为什么需要验证}
**验证方法**: {怎么做}
**代码原型**:
```{language}
{关键代码片段}
```
**验证结果**: ✅通过 / ❌不通过 / ⚠️有条件通过
**结论**: {详细说明}
**发现的新约束**: {如有}

### Spike-2: {技术点名称}
{同上格式}

## 总结
- 通过: X 项
- 不通过: X 项
- 有条件通过: X 项
- 新发现风险: X 项

## 路由建议
- [ ] 全部通过 → 继续入库
- [ ] 部分不通过 → 回退架构设计调整
- [ ] 全部不通过 → 回退架构设计重做
```

## 产出物
| 文件 | 说明 |
|------|------|
| SPIKE-REPORT.md | 技术验证报告 |
| spike-*/ | 各 Spike 原型代码目录（可选） |

## 检查项（脚本强制）
- [ ] SPIKE-REPORT.md 存在且 ≥20 行
- [ ] 每个 Spike 有明确结论（通过/不通过/有条件通过）
- [ ] 路由建议存在
- [ ] 总耗时 ≤ 4h

## 约束
- Spike 时间上限 4 小时，超时视为不通过
- 只验证关键技术点，不做完整实现
- 验证代码不合并到主分支
- 只在有高风险标记时触发（无高风险则跳过）
