# Stage 4: 技术 Spike（可行性验证）

## 任务

针对架构设计中识别出的高风险技术点，进行快速原型验证，确认技术方案可行后再进入下一阶段。

## 执行流程

1. 读取 ARCHITECTURE.md 中标记为「高风险」或「需验证」的技术点
2. 对每个风险点执行 Spike 验证：
   - 搭建最小可运行原型
   - 验证关键技术 API/库/框架的可行性
   - 记录验证结论（通过/不通过/有条件通过）
3. 产出 SPIKE-REPORT.md，包含：
   - 验证的技术点清单
   - 每个点的验证方法、代码片段、结论
   - 发现的新风险或约束
4. 结论路由：
   - 全部通过 → 推进下一阶段
   - 部分不通过 → 回退架构设计，针对性调整
   - 全部不通过 → 回退架构设计，重新设计

## 产出物

| 文件 | 说明 |
|------|------|
| SPIKE-REPORT.md | 技术验证报告 |
| spike-*/ | 各 Spike 原型代码目录（如有） |

## 时间盒控制

| 规则 | 说明 |
|------|------|
| 时限 | ≤4h（超时视为失败，触发回退） |
| 目标 | 最小可行验证，不是完整实现 |
| 产出 | 结论 + 代码原型（如有） |

## 三路决策

### ✅ 成功
核心功能完全可行，无重大限制。
**处理：** 继续后续阶段，Spike结论附入架构文档。

### 🟡 部分成功
核心功能可用，但存在已知限制。
**报告必须包含：**
- 限制清单
- 变通方案
- 影响评估
**决策：** 接受限制继续 / 调整方案 / 简化需求

### ❌ 失败
技术方案不可行。
**处理：** 回退到架构设计，寻找替代方案。

## 约束

- Spike 时间上限 4 小时，超时视为不通过
- 只验证关键技术点，不做完整实现
- 验证代码不合并到主分支
- SPIKE-REPORT.md 必须存在且结论明确
