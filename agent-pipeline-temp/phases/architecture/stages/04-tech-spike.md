# 技术 Spike 阶段指令

你执行技术 Spike 验证。不要问"要继续吗"，收到任务直接执行。

## 前置条件
- ARCHITECTURE.md 已存在且用户已审阅确认
- ARCHITECTURE.md 包含高风险标记（`<!-- HIGH-RISK -->`、`<!-- SPIKE -->`、`<!-- RISK -->`、`高风险`、`需验证`）

## 必读文件
1. ARCHITECTURE.md — 重点看高风险标记部分
2. PRD.md — 理解需求上下文

## 任务

针对架构设计中识别出的高风险技术点，进行快速原型验证，确认技术方案可行后再进入任务分解。

## 执行流程

1. 读取 ARCHITECTURE.md 中标记为「高风险」或「需验证」的技术点
2. 对每个风险点执行 Spike 验证：
   - 搭建最小可运行原型
   - 验证关键技术 API/库/框架的可行性
   - 记录验证结论（通过/不通过/有条件通过）
3. 产出 SPIKE-REPORT.md，包含：
   - 验证的技术点清单
   - 每个点的验证方法、代码片段、结论
   - 发现的新风险或约束

## 验证方法

### 每个风险点的验证步骤
1. **定义验证目标**：明确要验证什么（API 兼容性？性能瓶颈？第三方服务稳定性？）
2. **最小原型**：写最少的代码验证核心技术点
3. **记录结果**：通过/不通过/有条件通过，附上代码片段和日志
4. **发现新风险**：验证过程中发现的额外风险或约束

### 常见 Spike 类型

| 类型 | 验证方式 | 产出 |
|------|---------|------|
| API 兼容性 | 调用第三方 API，验证请求/响应格式 | 调用代码 + 响应日志 |
| 性能瓶颈 | 压测关键接口，验证 QPS/响应时间 | 压测脚本 + 性能数据 |
| 框架可行性 | 搭建最小 Demo，验证框架特性 | Demo 代码 + 运行结果 |
| 数据库方案 | 验证索引策略/查询性能 | SQL + 执行计划 |
| 安全方案 | 验证认证/加密方案可行性 | 实现代码 + 测试结果 |

## 结论路由

| 情况 | 路由 |
|------|------|
| 全部通过 | 推进到 arch-finalize |
| 部分不通过 | 回退到 arch-design，针对性调整架构 |
| 全部不通过 | 回退到 arch-design，重新设计 |

## 约束

- **时间上限 4 小时**，超时视为不通过
- 只验证关键技术点，不做完整实现
- 验证代码不合并到主分支
- 每个风险点必须有明确结论
- 发现的新风险或约束必须记录

## 完成标志

SPIKE-REPORT.md 写完后，根据结论路由决定下一步。
