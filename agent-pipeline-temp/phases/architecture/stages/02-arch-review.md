# 阶段2: 架构交叉评审（arch-review）

## 任务
4个角色并发评审架构方案，从不同视角提出意见。架构师修改后，评审者复审确认。

## 前置条件
- `arch-design` 步骤已完成
- ARCHITECTURE.md 存在且通过基础校验

## 必读文件
1. ARCHITECTURE.md（架构方案）
2. PRD.md（需求文档）

## 评审角色与维度

| 角色 | 评审视角 | 重点检查 |
|------|---------|---------|
| **RD（开发）** | 技术可行性 | 技术选型合理性、接口设计、过度设计、逻辑缺陷 |
| **架构师** | 架构一致性 | 分层合规、模块耦合、设计模式、扩展性 |
| **QA** | 可测试性 | 测试覆盖、日志监控、自动化、故障注入 |
| **PM** | 需求完整性 | PRD 覆盖率、优先级合理性、逻辑闭环 |

## 执行流程

### 第一轮：独立评审
1. 四个角色独立评审 ARCHITECTURE.md
2. 每个角色输出评审意见到 cross-review-arch.md
3. 评审格式遵循 `references/arch-adversarial-review.md`

### 第二轮：架构师修订
4. 架构师根据评审意见修改 ARCHITECTURE.md
5. 记录修改内容和理由

### 第三轮：复审确认
6. 四个角色复审修改后的 ARCHITECTURE.md
7. 确认各自提出的问题已修复
8. 复审通过 → 推进；仍有问题 → 再改（最多 2 轮）

## 产出物
| 文件 | 说明 |
|------|------|
| cross-review-arch.md | 四个角色独立评审意见 |
| re-review-arch.md | 四个角色复审确认（如需要） |

## 评审输出格式

```markdown
## 架构交叉评审报告

### RD 评审（技术可行性）
#### 🔴 阻断项
- [ ] 问题描述 → 建议修复

#### 🟡 风险项
- [ ] 问题描述 → 建议修复

#### 🟢 观察项
- 观察内容

#### 评分: X/10

---

### 架构师评审（架构一致性）
#### 🔴 阻断项
...

---

### QA 评审（可测试性）
#### 🔴 阻断项
...

---

### PM 评审（需求完整性）
#### 🔴 阻断项
...

---

### 一致性检查
- 各视角是否有分歧：是/否
- 分歧详情：（如有）

### 总结
- 🔴 阻断项总数: X
- 🟡 风险项总数: X
- 结论: 评审通过 / 评审未通过
```

## 检查项（脚本强制）
- [ ] cross-review-arch.md 存在且 ≥30 行
- [ ] 4个角色各有独立评审段落
- [ ] 每个角色有评分
- [ ] 阻断项/风险项/观察项分类清晰
- [ ] 一致性检查段落存在

## 约束
- 总轮次 ≤2（初审 + 复审算 1 轮）
- 评审只发现问题，不修改 ARCHITECTURE.md（修改由架构师做）
- 阻断项 = 0 时，评审自动通过
- 阻断项 > 0 时，架构师必须修复后重审
