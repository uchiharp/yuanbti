# Stage 2: 架构交叉评审

## 任务

各角色并发评审架构方案，从不同视角提出意见。架构师修改后，评审者复审确认。

## 必读文件

1. ARCHITECTURE.md
2. PRD.md

## 评审角色与维度

| 角色 | 评审视角 |
|------|---------|
| 开发1 | 技术可行性：技术选型、接口合理性、过度设计、逻辑 bug |
| 开发2 | 技术实现：代码结构、模块划分、技术债、逻辑 bug |
| QA | 可测试性：测试覆盖、日志监控、自动化、逻辑 bug |
| PM | 需求完整性 + 逻辑闭环：PRD 覆盖、优先级、逻辑不闭环/冲突/漏洞/逻辑 bug |

## 执行流程

1. 四个角色并发评审，产出 cross-review-arch.md
2. 架构师根据意见修改 ARCHITECTURE.md
3. **评审者复审**：四个角色确认各自提出的问题已修复
4. 复审通过 → 推进下一阶段；仍有问题 → 架构师再改（最多 2 轮）

## 产出物

| 文件 | 说明 |
|------|------|
| cross-review-arch.md | 四个角色独立评审意见 |
| re-review-arch.md | 四个角色复审确认（如有） |

## 评审报告格式

```markdown
## 架构交叉评审报告

### 🔴 阻断项（必须修复才能继续）
- [角色] 问题描述 → 建议修复方式

### 🟡 风险项（建议修复，可带风险继续）
- [角色] 问题描述 → 建议修复方式

### 🟢 观察项（供下游参考）
- [角色] 观察内容

### 一致性检查
- 各角色是否有分歧：是/否
- 分歧详情：（如有）

### 结论
- [ ] 评审通过
- [ ] 评审未通过（阻断项 > 0）
```

## 约束

- 总轮次 ≤2（初审 + 复审算 1 轮）
- 评审只发现问题，不修改 ARCHITECTURE.md
- 阻断项 = 0 时，评审自动通过
- 阻断项 > 0 时，需要用户决定：修复后重评 / 带风险继续
